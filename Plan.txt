# Support and Lead-Gen Chatbot with an Eval Gate: Project Plan

## 1. What You're Building

A website chatbot for one business that answers support questions from its knowledge base (with citations), captures leads politely and with consent, hands off to a human when needed, and is protected by a CI check that blocks any change that makes answers worse.

**In scope:** hybrid retrieval, grounded answers with citation checking, abstention ("I don't know"), LangGraph orchestration, lead capture, human handoff, FastAPI service, eval suite, GitHub Actions gate, feedback-to-review loop, live deployment, demo video.

**Out of scope for the core:** multi-tenancy, Graph RAG, fine-tuning, voice, a fancy UI. Semantic caching and a reranker are stretch goals (section 10).

## 2. Key Decisions

| Decision | Choice | Why |
|---|---|---|
| Business | A fictional business you write the KB for (for example a dental clinic: services, prices, insurance, hours, cancellation policy) | Full control over facts, so golden answers are verifiable, and no license issues |
| Database | One Postgres with pgvector for chunks, leads, feedback, and eval results | Postgres full-text search plus pgvector gives hybrid search with no separate search engine |
| Lexical search | Postgres full-text search | It is not true BM25. Say so in your README |
| Orchestration | LangGraph | Real uses: conditional routing, a slot-filling loop, persistence, human interrupt |
| API | FastAPI with streaming over SSE | SSE is plain HTTP, which avoids WebSocket restrictions on some free tiers |
| Embeddings | Hosted embedding API behind an interface | A small free host can't comfortably load a local embedding model; cost for this corpus is tiny |
| LLM | One small, cheap chat model behind a thin interface | Swappable; avoids hard-coding a vendor |
| Judge | A different model than the generator, temperature 0 | Reduces self-preference bias and noise |

## 3. Architecture

```
 Website widget (HTML/JS, SSE)
        │
        ▼
 FastAPI  /v1/chat ──► LangGraph (state saved per thread_id in Postgres)
                          │
   classify_intent ───────┼──► support ─► rewrite_question ─► retrieve (hybrid)
                          │                    ─► generate (citations) ─► verify
                          │                              │ ok          │ fail
                          │                           respond       abstain / handoff
                          ├──► lead ─► collect_slots (loop) ─► consent ─► save_lead
                          ├──► handoff ─► interrupt() ─► wait for human reply
                          └──► out_of_scope ─► polite refusal

 Every turn logs: latency, tokens, cost, retrieval IDs, verifier result
 Thumbs-down / abstain / handoff ─► candidates table ─► you review ─► golden set
```

### LangGraph notes

- A human interrupt needs a checkpointer (in-memory for dev, Postgres for production), a thread ID in the config, and JSON-serializable payloads. Without a persistent checkpointer, `interrupt()` raises an error.
- When the graph resumes, the node restarts from the beginning, so all code before `interrupt()` re-runs. Keep side effects (saving a lead, sending a notification) after the interrupt and make them idempotent.
- Check the LangGraph persistence docs for the Postgres saver import path and its one-time setup call, since package layouts change.

```python
# Sketch: graph wiring (names are yours to choose)
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command

class ChatState(TypedDict):
    thread_id: str
    messages: list
    intent: str
    standalone_q: str
    chunks: list
    answer: dict          # text, citations, confidence
    lead: dict            # need, budget, timeline, name, contact, consent
    handoff: bool

def human_handoff(state: ChatState):
    reply = interrupt({"thread": state["thread_id"], "context": state["messages"][-6:]})
    return {"messages": state["messages"] + [("assistant", reply)]}

g = StateGraph(ChatState)
g.add_node("classify", classify_intent)
g.add_node("rewrite", rewrite_question)
g.add_node("human_handoff", human_handoff)
# ... add the other nodes ...
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route_by_intent,
                        {"support": "rewrite", "lead": "collect_slots",
                         "handoff": "human_handoff", "other": "refuse"})
graph = g.compile(checkpointer=checkpointer)

# Resume a paused thread:
# graph.invoke(Command(resume=human_text), {"configurable": {"thread_id": tid}})
```

## 4. Data

### 4.1 Knowledge base (about 30-40 short documents)

Write or edit these yourself. An LLM can draft them, but you must reconcile every fact. Build in traps so retrieval is non-trivial:

- Exact identifiers: service codes, insurance plan names, form numbers.
- An old price list next to a current one, with the old one marked superseded.
- Facts spread across two pages (a service page plus a policy page).
- A table (hours, pricing).
- Things the KB deliberately does not say, so unanswerable questions exist.

### 4.2 Golden set: 50 cases to start

| Type | Count | Correct behavior |
|---|---|---|
| Direct lookup | 18 | Correct answer with correct citation |
| Exact identifier | 5 | Finds it (full-text search should shine) |
| Multi-source | 6 | Combines two documents |
| Follow-up using history | 3 | Resolves "what about for kids?" correctly |
| Unanswerable | 8 | Abstains, offers handoff |
| Ambiguous | 3 | Asks a clarifying question |
| Safety: injection, off-topic, "promise me a discount" | 7 | Refuses, never invents prices or promises |

Plus **8 scripted lead conversations**, kept in a separate file.

Hold out about 20% of cases as a **holdout split**. Never look at their results while tuning prompts, and report them separately. Otherwise you are just tuning to your own test.

Write every golden answer by hand from the KB. Do not generate them with an LLM.

```json
{
  "id": "q-017",
  "dataset_version": "1.0.0",
  "split": "dev",
  "type": "lookup",
  "question": "Do you take Delta Dental, and what's covered for a cleaning?",
  "gold_doc_ids": ["insurance/accepted-plans#delta", "services/cleaning#coverage"],
  "golden_answer": "...written by you from the KB...",
  "must_abstain": false,
  "notes": "Needs two sources; tests the superseded price list trap."
}
```

## 5. Database and Hybrid Retrieval

Use a generated `tsvector` column for the lexical side and an HNSW index with cosine ops for vectors (the vector dimension must match your embedding model). Merge the two ranked lists with Reciprocal Rank Fusion (RRF): each result scores `1 / (60 + rank)` per list, and a FULL OUTER JOIN keeps documents found by only one method.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          BIGSERIAL PRIMARY KEY,
  tenant_id   TEXT NOT NULL DEFAULT 'default',
  doc_id      TEXT NOT NULL,          -- stable, e.g. 'services/cleaning#coverage'
  title       TEXT NOT NULL,
  content     TEXT NOT NULL,
  embedding   vector(1536),           -- must match your embedding model
  kb_version  TEXT NOT NULL,
  fts tsvector GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
    setweight(to_tsvector('english', coalesce(content,'')), 'B')) STORED
);
CREATE INDEX ON chunks USING GIN (fts);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
```

```sql
-- Hybrid query sketch: $1 = query text, $2 = query embedding, $3 = limit
WITH lexical AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(fts, q) DESC) AS rank
  FROM chunks, websearch_to_tsquery('english', $1) AS q
  WHERE fts @@ q
  ORDER BY ts_rank_cd(fts, q) DESC
  LIMIT 50
),
semantic AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $2::vector) AS rank
  FROM chunks
  ORDER BY embedding <=> $2::vector
  LIMIT 50
)
SELECT c.id, c.doc_id, c.content,
       coalesce(1.0 / (60 + lexical.rank), 0.0) +
       coalesce(1.0 / (60 + semantic.rank), 0.0) AS score
FROM lexical
FULL OUTER JOIN semantic USING (id)
JOIN chunks c USING (id)
ORDER BY score DESC
LIMIT $3;
```

Other tables: `conversations`, `messages`, `leads` (with `consent_at`), `feedback`, `candidates`, `eval_runs`, `eval_results`. Use plain SQL migrations or Alembic.

## 7. Evaluation

| Area | Metric | How |
|---|---|---|
| Retrieval | recall@5, MRR | Gold doc IDs vs. retrieved; compare dense-only, full-text-only, hybrid |
| Answer | correctness (pass/fail) | Judge against your golden answer |
| Grounding | faithfulness | Claims supported by retrieved text |
| Citations | citation accuracy | Verifier on each cited claim |
| Abstention | precision and recall | On unanswerable and answerable cases |
| Lead gen | slot accuracy; **consent violations (must be 0)**; "pushy" check | Scripted conversations |
| Safety | pass rate (must be 100%) | Injection, off-topic, promise traps |
| Ops | p50/p95 latency, tokens, cost per conversation | Logged per turn |

### Making the numbers trustworthy

1. **Validate your judge.** Hand-label 30 answers and report how often the judge agrees with you. If agreement is poor, fix the judge prompt first.
2. **Measure noise.** Run the baseline twice at temperature 0 and see how much scores differ. Set CI thresholds above that noise.
3. **Cache LLM calls** in eval runs (keyed by prompt hash) so unchanged pieces are free and deterministic.
4. **Report by question type,** not only overall.

### Experiments to run (record in `docs/results.md`)

- Dense vs. full-text vs. hybrid
- Heading-aware chunks vs. fixed-size chunks
- With vs. without citation verification (faithfulness delta)
- Abstention threshold sweep (precision/recall curve)

## 8. CI Quality Gate

Trigger on PRs that touch `src/`, `prompts/`, `configs/`, `data/kb/`, or `evals/`.

```yaml
name: eval-gate
on:
  pull_request:
    paths: ["src/**", "prompts/**", "configs/**", "data/kb/**", "evals/**"]
permissions:
  contents: read
  pull-requests: write
jobs:
  eval:
    runs-on: ubuntu-latest
    env:
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/postgres
      LLM_API_KEY: ${{ secrets.LLM_API_KEY }}
    services:
      postgres:
        image: pgvector/pgvector:pg16     # pin a version you tested
        env:
          POSTGRES_PASSWORD: postgres
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - run: pip install -e ".[dev]"
      - run: make ingest
      - run: make eval-ci            # writes evals/runs/pr.json
      - name: Compare to baseline
        run: |
          python -m evals.compare \
            --baseline evals/baseline.json \
            --candidate evals/runs/pr.json \
            --comment-out comment.md
      - name: Comment on PR
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file comment.md
        env:
          GH_TOKEN: ${{ github.token }}
      - name: Enforce gate (non-zero exit blocks merge)
        run: |
          python -m evals.compare \
            --baseline evals/baseline.json \
            --candidate evals/runs/pr.json \
            --enforce
```

### Gate rules (put them in `configs/gate.yaml`)

- **Hard fails:** any consent violation, any safety-suite failure, abstention recall below a floor.
- **Soft fail:** a headline metric drops more than N points vs. baseline (choose N after measuring noise; start around 5).
- The PR comment lists metric deltas and the exact cases that flipped from pass to fail.
- **Changing the baseline is a deliberate PR** (`make eval-baseline`), reviewed like code. Turn on branch protection so the check is required.
- PR runs from forks don't receive repository secrets, which doesn't matter for a solo repo.

## 9. Feedback Loop and Dataset Growth

1. `POST /v1/feedback` and automatic signals (abstained, handoff requested, citation check failed) write rows to `candidates`.
2. `make review` is a small CLI that shows the question, the bot's answer, and the retrieved chunks, and asks you to accept (and type the correct answer), reject, or defer.
3. Accepted cases are appended to `evals/golden/` with a new dataset version and a changelog entry.
4. Never auto-add unverified answers, or your tests become circular.
5. Show it working in the demo: a real failure becomes a test, the test fails, you fix the prompt, and it passes.

## 11. Deployment

- **API:** Docker image on a free-tier host. Free tiers change often, so verify before you commit. One comparison checked in September 2026 found that Fly.io no longer has a free allowance (only a short trial), and another source says Render's free web services sleep after 15 minutes and take 30-50 seconds to cold start, with free Postgres expiring after 90 days.
- **Database:** use a separate free Postgres with pgvector (Neon and Supabase both list pgvector support) instead of relying on a host's expiring database.
- **Cold starts:** mention them in the README, and record the demo video as a backup so a sleeping server never costs you a recruiter's visit.
- **Secrets:** environment variables only, never committed. Set a hard monthly spend limit on your LLM provider key.
- **Cost:** a 50-case eval run should cost cents. Check current pricing and cache aggressively.

## 15. Risks

| Risk | Mitigation |
|---|---|
| Judge noise makes CI flaky | Temperature 0, measure variance, set thresholds above it, cache calls |
| Overfitting prompts to the golden set | Holdout split; report both |
| Prompt injection via users or KB text | Safety suite; treat retrieved text as data, never as instructions |
| Storing personal data | Consent before saving, delete endpoint, don't log contact details |
| Scope creep | Follow the cut order in section 10; stretch goals only after the done checklist |
| API cost surprises | Provider spend cap, call caching, small models for judging |
